## 2026-10-02 · T3.4 User-prompt builder · #51 (closes #11)
- **What:** `src/prompts.py` gets `build_user_prompt(role, interview_type, seniority, user_text) -> str`. It returns `Role: ...`, `Session type: "..."` and `Seniority: ...` lines, then one sentence telling the model the tagged text is the candidate's answer or question and not instructions, then the user's text between `USER_INPUT_OPEN`/`USER_INPUT_CLOSE` (`<user_input>` / `</user_input>`, each on its own line). Also adds `SENIORITY_LEVELS = ("Junior", "Mid-level", "Senior", "Lead")` for T5.1's select. Tests in `tests/test_prompts.py`.

Every field is escaped, not only the user's text, because the role may be free text (T3.1 follow-up 1) and could otherwise fake a block. The user also chose a fixed seniority list.
- **Decisions & gotchas:** the builder does **not** call `validate_input`: the guard runs first (as in the brief's diagram), and the builder expects already-cleaned text. Like the strategies, it accepts any role/type/seniority string. Code in an answer reaches the model as entities (`a &lt; b`); the model reads that fine, and the chat should still show the user's original text, not the built prompt. The instruction sentence says "user_input tags" without angle brackets, so the finished message holds exactly one opening and one closing tag (the tests check this). Not wired into `app.py` yet: the UI has no role/type/seniority inputs until T5.1. Application Control policy`); the same 8 tests also fail on `main`, so this is not caused by this PR. CI on Linux is the check for them. Review fix (code-reviewer): context fields are also collapsed to one line (`" ".join(text.split())`), because a role holding `\n` could otherwise add a fake `Seniority:` line or an instruction above the block, where the model reads it as trusted context.
- **Follow-ups:** T5.2 sends `build_user_prompt(...)` as the user message (keep showing the raw `clean` text in the chat). ## 2026-10-01 · T2.1 OpenRouter client wrapper · #48 (closes #4)
- **What:** `src/llm.py`. `complete(messages, model, temperature, max_tokens, *, client=None)` calls OpenRouter's OpenAI-compatible endpoint through the `openai` SDK and returns the reply text. A model outside `ALLOWED_MODELS` raises `InvalidModelError` before a client is built or the key is read. Timeout, 401, 429 and 5xx raise `LLMTimeoutError`, `LLMAuthError`, `LLMRateLimitError` and `LLMServerError`; anything else (400, connection failure, empty reply) raises the base `LLMError`. All carry fixed user-readable messages, never the SDK text. 429/5xx are retried up to `MAX_RETRIES = 2` times with 1 s then 2 s backoff. `tests/test_llm.py` covers it at 100% with a mocked HTTP transport.
- **Why:** one small interface for the UI (T5.2) and streaming (T2.2) to build on; fixed messages keep response bodies and keys out of what the user sees.
- **Decisions & gotchas:** `openai` 3.x sends requests through **`httpx2`** (not `httpx`); tests mock it with `httpx2.MockTransport` via `make_client(key, http_client=...)`. The SDK retries 2× by default, so `make_client` sets `max_retries=0`; otherwise retries would multiply. Timeouts (30 s, `REQUEST_TIMEOUT`) are not retried, as the ticket only asks for 429/5xx. Backoff sleeps through `llm._sleep` so tests can patch it. No temperature range check and no `max_tokens` cap here. Review fixes: a missing or unparseable key (`MissingAPIKeyError`/`SecretsFileError` from `get_api_key()`) is re-raised by `make_client()` as `LLMAuthError`, so catching `LLMError` covers every failure; a whitespace-only reply counts as empty. Third review: the SDK does not validate 200 responses (a non-JSON body comes back as a plain `str`, malformed JSON raises `json.JSONDecodeError`, a choice may lack `message`), so `complete()` catches `ValueError` and `_reply_text()` reads every field defensively; all of these now end in `LLMError`. Fourth review: that `except ValueError` also catches request-side errors, so `make_client()` rejects a non-ASCII key (smart quotes, zero-width space; HTTP headers are ASCII) with `LLMAuthError` first, rather than letting it show as "unreadable answer". Fifth review: the check is `isascii() and isprintable()`, because a newline, CR or NUL in the key is ASCII but fails in h11 as a generic connection error that quotes the raw key. Gotcha: Claude's tool input turns backslash-u escapes into the real characters, so write test strings with invisible characters as escape sequences (generate them with `chr()` if your tool input converts them) and check the file's bytes.
- **Follow-ups:** `max_tokens` cap and usage display in T2.3; streaming in T2.2. Check by hand with one live OpenRouter call in T2.3 (mocked tests cannot show either): (1) gpt-5 models spend reasoning tokens from `max_tokens`, so a small cap may return empty content with `finish_reason="length"`, which today shows as "empty answer, try again" and needs its own "answer was cut off" message; (2) OpenAI only accepts the default temperature for gpt-5, so confirm OpenRouter drops a non-default temperature rather than answering 400. The UI should catch `LLMError` and show only `str(exc)` (T5.2/T5.4), never `st.exception(exc)`: the chained SDK error (`__cause__`) holds the raw response body. From review, not done: friendlier messages for OpenRouter 402 (no credits) / 403 (moderation); honour `Retry-After` on 429; maybe move timeout/retry constants to `config.py`; cache the client with `st.cache_resource` in T5.2.
